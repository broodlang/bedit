# Spacing systems, rhythm and density for a cell-grid editor UI

## Spacing scales: 4/8-pt grids, baseline grids, modular scales, and how major design systems define spacing tokens

### Takeaway
Every major system defines a small, closed set of named spacing steps built on one base unit (4 or 8 px), with a few sub-unit steps (2, 4, 6 px) for fine detail. The main reason given is fewer choices, less fiddling and more consistency. In a cell grid the natural base unit is the cell itself: line height vertically and the cell width horizontally. The scale should be a handful of named cell multiples plus at most one or two explicit sub-cell steps.

### Cited Findings
- spec.fm's 8-pt grid primer: "Use multiples of 8 to define dimensions, padding, and margin of both block and inline elements". Its rationale: "By removing 7 of every 8 spacing options, you reduce the amount of fiddling available to you and subsequently reduce speed to code." — [spec.fm, The 8-Point Grid](https://spec.fm/specifics/8-pt-grid)
- spec.fm distinguishes a **hard grid** (elements snapped to fixed 8-pt grid positions, grouped in containers, a natural fit for Material) from a **soft grid** (only the distances *between* elements are multiples of 8, which suits code and iOS, where system elements don't sit on an even grid). — [spec.fm](https://spec.fm/specifics/8-pt-grid); same distinction in [Hard and Soft 8 Point Grids (Sketch App Sources, Medium)](https://medium.com/sketch-app-sources/hard-and-soft-8-point-grids-60cf803b9de4) and [Why Manifold uses an 8pt grid](https://medium.com/manifoldco/why-manifold-uses-an-8pt-grid-b068e9287ba9). Manifold prefers the soft grid.
- spec.fm pairs the 8-pt UI grid with a **4-pt baseline grid** for text ("I like to combine my 8pt UI grid with a 4pt baseline grid"). It notes text doesn't need every point aligned to the pixel grid, because anti-aliasing keeps letters readable. — [spec.fm](https://spec.fm/specifics/8-pt-grid)
- **IBM Carbon** spacing scale: `$spacing-01..13` = 2, 4, 8, 12, 16, 24, 32, 40, 48, 64, 80, 96, 160 px, built from multiples of 2, 4 and 8 to complement its 2x Grid and type scale. Small steps serve detail-level relationships and large steps control density. The same tokens are used inside components and between them. Layout uses the Stack component's `gap` rather than component margins. Tokens don't change with screen size; at a breakpoint you step up or down the scale (e.g. `$spacing-05` → `$spacing-03`). Off-scale values are "allowed in rare cases but should be avoided". — [Carbon spacing overview](https://carbondesignsystem.com/elements/spacing/overview/)
- **Atlassian** base unit is 8 px = `space.100`. The numeric suffix is a percentage of the base (`space.200` = 16 px). Steps: 0, 2 (`025`), 4 (`050`), 6 (`075`), 8, 12, 16, 20, 24, 32, 40, 48, 64, 80, plus negative steps from -2 to -32 for bleeding out of container padding (the Bleed primitive is preferred). Usage bands: 0–8 px for compact UI (icon-to-text gaps, input padding, table cells, spacing within cards), 12–24 px for less dense components, 32–80 px for page layout. Tokens "should be used in place of the raw pixel or REM values". Layout principles: put related items closer together, use consistent spacing in lists to create rhythm, and apply optical adjustments where balance needs them. The stated rationale includes later support for adjustable density. — [Atlassian spacing foundations](https://atlassian.design/foundations/spacing)
- **Shopify Polaris** uses a 4 px base. Primitive tokens are named by percentage multiplier (`space-100` = 4 px, `space-400` = 16 px). Space tokens are only for padding, margin and gap, not for height, width or outline-offset. "Always use semantic tokens over primitive ones when possible." — [Polaris layout tokens](https://polaris.shopify.com/design/layout/layout-tokens) (via search snippet; the page now redirects to shopify.dev). Note: an older Polaris page names the same 4 px value `--p-space-1`, so token names have changed across versions. — [Polaris space (archived mirror)](https://ss-polaris.vercel.app/design/space)
- **Material 3**: the official m3.material.io spacing page would not render for fetching. Secondary sources (Flutter packages) describe M3 spacing tokens on a **4dp grid** and an M3 Expressive regular-density scale of 4/8/12/16/24/32. — [material_design Flutter package](https://pub.dev/packages/material_design); [M3ESpacing class](https://pub.dev/documentation/material_3_expressive/latest/foundations_m3e_spacing/M3ESpacing-class.html). These are not first-party.
- **Every Layout modular scale**: when text is the main content, `line-height` is the measure for white space. With font-size 1rem and line-height 1.5, the default space is 1.5rem and larger spaces are multiples of it. The scale comes from one ratio (`--ratio: 1.5`, `--s1 = --s0 * ratio`, smaller steps divide by the ratio): "Consistent, balanced design is seeded by simple axioms like the modular scale ratio." Harmony comes from sticking to the chosen ratio, not from which ratio it is. To enforce the scale, components accept only integer step indices for `padding`, interpolated into `var(--s${n})`, so authors can't pass arbitrary lengths. — [Every Layout: Modular scale](https://every-layout.dev/rudiments/modular-scale/)
- **Refactoring UI** (via secondary summaries; the book's text was not reached): prefer a hand-picked scale over a pure ratio scale for UI; adjacent steps should be at least about 25% apart; a typical 16 px-based scale is 4, 8, 12, 16, 24, 32, 48, 64, 96, 128; start with too much white space and remove it. — [Refactoring UI notes (rjseymour66)](https://rjseymour66.github.io/webdev/refactoring-ui/); [Presta: spacing in UI design](https://wearepresta.com/spacing-in-ui-design/)

### Inferences
- The systems agree on a few points: one base unit, a closed and named set of steps, sub-base steps reserved for detail (Carbon 2 px, Atlassian 2/4/6 px), steps that get further apart as they grow (about 25–50% apart at the top), and separate tokens for "inside a component" and "between components/layout".
- For bedit, the translation is: **vertical base = 1 row (line height), horizontal base = 1 cell (the advance width).** A row is about 1.25 × font size and a cell is about 0.6 × font size, so 1 row ≈ 2 cells physically. That 2:1 ratio is why TUIs pad 1 vertically and 2 horizontally (see the next section).
- A cell-grid scale might be: `0`, `hairline` (a fixed device-pixel line, not a cell fraction), `half` (0.5 row or cell, the only sub-cell step), `1`, `2`, `3`. This mirrors the "a few sub-unit steps plus base multiples" pattern. bedit today has many unrelated fractional constants, e.g. `*sb-hover-vinset* 0.16` and `*sb-hover-pad* 0.55` in `src/statusbar.blsp`, `*completion-card-radius* 0.5` in `src/completion.blsp` and `*scrollbar-width* 0.5` in `src/view.blsp`. 0.16 and 0.55 are exactly the off-scale values the design systems warn against (observed in local source, `grep` of `/home/wilhelm/src/broodlang/bedit/src`).
- The hard/soft grid distinction maps directly. The text area, mode line, header line and echo area are a **hard grid** (they must occupy whole rows). Popup interiors could be a soft grid, but any frame that occupies screen rows should snap to whole rows, so neighbouring regions never see a fractional gap.

### Gaps
- Could not render the official Material 3 or Material 2 spacing/density pages (JS-only), so the M3 4dp grid, the 4dp type baseline grid and the density scale (-1/-2/-3 each removing 4dp) are unconfirmed first-party. Treat them as commonly reported, not verified.
- The Refactoring UI book itself was not consulted; its numbers come from secondary summaries that differ slightly.
- Apple HIG layout page did not render; no first-party Apple spacing values were obtained (secondary sources claim 16 pt iPhone / 20 pt iPad margins and an 8 pt grid; unverified).

## Vertical rhythm with text: baseline grids, line height as the vertical unit, and how terminals/TUIs achieve calm

### Takeaway
In text-heavy layouts the standard advice is to derive vertical space from the line height. Every vertical gap should be a multiple, or at most a clean half, of one line, so all text stays on one baseline rhythm. Terminals get calm "for free" because cells are the only unit. They use whole-cell padding at a 2:1 horizontal-to-vertical ratio to compensate for tall cells.

### Cited Findings
- Every Layout: when text is the main content, `line-height` is the base for white space, and larger spaces are multiples of it (1.5rem, 3rem, 4.5rem). — [Every Layout: Modular scale](https://every-layout.dev/rudiments/modular-scale/)
- spec.fm recommends baselining text, i.e. placing each line's baseline on evenly spaced lines to create consistent vertical rhythm, using a 4-pt baseline grid under an 8-pt UI grid. — [spec.fm](https://spec.fm/specifics/8-pt-grid)
- *The Monospace Web* (Oskar Wickström) lays a whole web page onto a monospace character grid. The page shrinks in character-sized steps as the viewport narrows. Images and video get extra bottom padding "to maintain the monospace grid". Tables adjust to the grid, and a grid container's total width may be less than 100% so the grid is kept. Box-drawing ASCII in `<pre>` aligns to it. — [The Monospace Web](https://owickstrom.github.io/the-monospace-web/)
- **ratatui** `Padding::proportional(n)` gives left/right `2n` and top/bottom `n` (`proportional(1)` = `Padding::new(2,2,1,1)`). The docs say terminal cells are usually taller than wide, so doubling horizontal padding makes the spacing look even. — [ratatui Padding docs](https://docs.rs/ratatui/latest/ratatui/widgets/block/struct.Padding.html); [ratatui 0.26.3 padding.rs](https://docs.rs/crate/ratatui/0.26.3/source/src/widgets/block/padding.rs)
- **Textual** expresses `padding`/`margin` as `<integer>` values (cells in practice; the docs don't say so), with padding inside the widget and margin around it, CSS box-model style. Its own example uses `padding: 4 8`, again a 1:2 vertical:horizontal ratio, though the docs don't explain it. — [Textual padding docs](https://textual.textualize.io/styles/padding/)

### Inferences
- A cell grid already is a baseline grid: each row is one line-height and every text baseline sits at the same offset in its row. Rhythm breaks only when something is offset by a non-row amount (a 6 px window inset at the top, a fractional-row popup, a header line drawn at a fractional y). After that, every row below that boundary is off the rhythm of the rows above it, or a sliver gap appears at the edge. This is the likely mechanism behind the "gap above the header line" and "uneven gap under the echo area" bugs. The leftover window height (window px minus inset, modulo row height) has to go *somewhere* explicit: one named place, e.g. the bottom edge below the echo area, never split ad hoc.
- Rule for bedit: **vertical offsets that affect where text rows sit are whole rows. Sub-row values are allowed only for decoration inside a row** (a hover pill's inset, a hairline, a selection pill's radius), and they must not move any text baseline.
- The horizontal unit should be the cell, and "visually equal" padding on a box is `1 row` vertical to `2 cells` horizontal (ratatui's proportional rule). Equal *cell counts* on all four sides (e.g. bedit's popup card with "one cell of padding on EVERY edge", `src/view.blsp` comment near line 2789) look *thinner* left/right than top/bottom on a 1.25-line-height font, because one cell is about half a row physically. That is either a deliberate choice or the source of "popups whose padding differs".
- A terminal's calm comes from (a) one unit, (b) whole-cell borders and padding, (c) alignment to columns. bedit can get the same calm by refusing fractional placement for anything that holds text.

### Gaps
- No primary source found that measures calm or legibility from vertical rhythm. It is a long-standing typographic convention, argued rather than tested.
- Textual's docs don't state cell semantics or the aspect-ratio rationale explicitly.

## Density: compact vs comfortable modes and research on information density

### Takeaway
Editors implement density as one global multiplier or switch applied to *chrome* spacing (toolbars, headers, list rows, tabs), never to the text grid. Zed uses 0.75 / 1.0 / 1.25, JetBrains has a Compact Mode toggle, and VS Code has `window.density.*`. The most useful theory (Matt Ström) is that perceived density is value per unit of space and time, not raw items per pixel.

### Cited Findings
- **Zed** `UiDensity` enum (still marked experimental): `Compact` (tighter spacing, smaller elements), `Default`, `Comfortable` (more spacing, larger elements). The spacing ratios are 0.75, 1.0 and 1.25, and a TODO notes the ratio "is not standardized throughout the app". Config strings are `"compact"`, `"default"`, `"comfortable"`. — [Zed source, crates/theme/src/ui_density.rs (mirror)](https://git.secluded.site/zed/blob/main/crates/theme/src/ui_density.rs?raw=1)
- **JetBrains** New UI Compact Mode (View | Appearance | Compact Mode): "reduced heights for toolbars and tool window headers, scaled-down spacings and paddings, and smaller icons and buttons." — [JetBrains IDE viewing modes](https://www.jetbrains.com/help/clion/ide-viewing-modes.html.md); [Rider New UI](https://www.jetbrains.com/help/rider/New_UI.html). A support thread gives unofficial row-height overrides of about 22 (compact) vs 24 (default) for lists and trees. — [JetBrains support thread](https://intellij-support.jetbrains.com/hc/en-us/community/posts/18492517107858/comments/18501784139538) (unofficial, may change)
- **VS Code**: `window.density.layout` controls "spacing around major editor parts". It requires `workbench.experimental.modernUI` and is set from Customize Layout. `workbench.activityBar.compact` is a separate setting. — [VS Code custom layout docs](https://code.visualstudio.com/docs/configure/custom-layout.md); news coverage of the Modern UI compact layout (Oct 2026): [Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/10/27/vs-code-modern-ui-preview-adds-compact-layout-connected-tabs.aspx)
- **Matt Ström, "UI Density"**: density is "the value a user gets from an interface divided by the time and space it occupies". Visual density (things per area) is an unreliable first judgment. Information density follows Tufte's data-ink ratio. Temporal density covers time and actions. Value density is the goal (Google 2001 vs Yahoo's portal). — [Matt Ström, UI density](https://mattstromawn.com/writing/ui-density/) (canonical: matthewstrom.com/writing/ui-density/, which returned 403); summary in [Gigazine](https://gigazine.net/gsc_news/en/20240526-ui-density)
- Atlassian lists adjustable UI density as a motivation for tokenising space at all. — [Atlassian spacing](https://atlassian.design/foundations/spacing)
- Material/Flutter offer density as discrete levels (`VisualDensity` standard/comfortable/compact). — [Flet VisualDensity docs](https://flet.dev/docs/types/visualdensity); [Material: Applying density](https://material.io/design/layout/applying-density.html) (not rendered)

### Inferences
- Density only works cleanly if spacing is tokenised first. A multiplier over raw numbers is unusable, and Zed's own TODO shows the cost of an unevenly applied ratio.
- In a cell grid a multiplier like 0.75 produces fractional cells. A grid-native density switch is instead a different *token table*: e.g. comfortable `popup.pad = 1 row × 2 cells`, compact `popup.pad = 0 rows × 1 cell`, and line height 1.25 vs 1.15. The text grid then re-derives everything. Changing line height is the strongest density lever for an editor, and because everything is measured in rows, all chrome scales with it automatically.
- Ström's framing argues against chasing compactness for its own sake. Calm comes from consistent rhythm and grouping (fewer distinct gap sizes), not from more or less whitespace.

### Gaps
- No peer-reviewed study specific to editor or IDE density was found. Evidence is vendor practice plus essays.
- The exact Zed settings key and per-element effects were not confirmed from Zed's user docs.

## Insets and padding consistency: equal padding, optical adjustment, Gestalt proximity, padding inside popups and menus

### Takeaway
Proximity is the governing law: spacing inside a group must be visibly smaller than spacing between groups, and a heading sits closer to what it labels. "Equal" padding should be *optically* equal, which on a cell grid means about 2 cells horizontally per row vertically. Deliberate asymmetries (icon side, edge side) should be named exceptions, not stray numbers.

### Cited Findings
- NN/g on proximity: "elements spaced apart are perceived as belonging to separate groups." Proximity can override colour and shape cues. Keep minimal space between a label and its field and "a larger margin before the next label-field pair". A heading should sit closer to its own content than to the preceding content. Whitespace can set off a different function (e.g. search beside nav links). — [NN/g, Proximity Principle](https://www.nngroup.com/articles/gestalt-proximity/)
- Atlassian names proximity grouping, list rhythm and "optical adjustments where visual balance requires them" as layout principles. — [Atlassian spacing](https://atlassian.design/foundations/spacing)
- Optical corrections often show up as **unequal** padding values (e.g. 1–2 px top vs bottom for uppercase text), and the advice is not to "fix" them back to equal in code review. — [UI/UX Atlas: optical vs geometric alignment](https://uiux-atlas.pages.dev/lessons/visual-design/optical-vs-geometric-alignment)
- Use less padding on the icon side of a button for balance. — [jakub.kr: Optical alignment](https://jakub.kr/components/optical-alignment); [Figma forum thread](https://forum.figma.com/archive-21/adjusting-for-optical-balance-when-using-layer-properties-for-button-icons-33007). Equal padding on all sides can make buttons look stubby; horizontal padding about 2× vertical is a common rule of thumb. — [The Admin Bar](https://theadminbar.com/5-ez-tricks/). These are rules of thumb, not studies.
- ratatui builds the 2:1 horizontal:vertical rule into `Padding::proportional` because cells are taller than wide. — [ratatui Padding](https://docs.rs/ratatui/latest/ratatui/widgets/block/struct.Padding.html)
- Carbon recommends layout spacing via a Stack's `gap` rather than per-component margins. Atlassian provides a Bleed primitive (negative space) for content that must break out of container padding. — [Carbon spacing](https://carbondesignsystem.com/elements/spacing/overview/); [Atlassian spacing](https://atlassian.design/foundations/spacing)

### Inferences
- **The container owns the gap.** Carbon's Stack/gap and Atlassian's Bleed both put spacing on the *parent* (padding plus gap between children), never on children's outer margins. Margins collapse and double up, and that is how a header line gets an extra gap above it: two neighbours each "owning" half of a separating space. For bedit this means the frame layout (window → header line → panes → mode line → echo area) should be one vertical stack of whole-row regions with an explicit gap table, and no widget should add space outside its own rect.
- **Popup/card rule:** padding is measured from the border's *inner* edge to the text, the same token on every card (`card.pad = [rows cols]`). Row inset inside a list item (bedit's `ui-row-inset`, default 1 cell, both sides, `src/ui-kit.blsp`) is a separate token from card padding. Both should come from the table, not from per-call `:inset 2` / `:gap 3` overrides (seen in `src/view.blsp` around line 2795).
- **Edge-side exception:** content next to the window edge or a scrollbar can take more padding on that side. It is optically needed, but it must be a named token (`edge.extra`) so it isn't confused with drift.
- **Proximity hierarchy as a check:** gap inside a group < gap between groups < gap between regions. With a scale of {0, ½, 1, 2} this is easy to state and test.

### Gaps
- No measured study of optimal popup padding ratios. All the guidance is practitioner convention.

## Encoding spacing as tokens and constraints so ad-hoc numbers can't creep in

### Takeaway
Design systems layer three defences: (1) a closed token vocabulary (primitive steps aliased by semantic names), (2) APIs that only accept token names or step indices, and (3) linters that flag raw values in spacing properties. The W3C DTCG format (stable since Oct 2025) standardises the token file shape, including aliases.

### Cited Findings
- **W3C Design Tokens Community Group format 2025.10**, the first stable version (announced 2025-10-28). `dimension` tokens have `$value: {value, unit}` with unit `px` or `rem`, and `unit` is required even for 0. Aliases use `{group.token}`, chains are allowed and cycles are errors. Groups are organisational only ("SHOULD NOT" be used to infer type). Primitive→semantic tiers are a usage pattern, not normative. — [DTCG Format 2025.10](https://www.designtokens.org/tr/2025.10/format/); [W3C announcement](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)
- **Atlassian ESLint** `ensure-design-token-usage` has a `domains` option (`color`, `spacing`, `shape`; default `['color']`, so spacing must be opted into). It flags e.g. `padding: '16px'` and suggests `token('space.200')`-style replacements. A separate `use-tokens-space` rule enforces space tokens over hard-coded values. A Stylelint plugin offers `{ color: true, spacing: true }`. — [Atlassian ESLint ensure-design-token-usage](https://atlassian.design/components/eslint-plugin-design-system/ensure-design-token-usage); [npm @atlaskit/eslint-plugin-design-system](https://www.npmjs.com/package/%40atlaskit%2Feslint-plugin-design-system); [Atlassian Stylelint plugin](https://atlassian.design/components/stylelint-design-system/configuration-and-setup)
- **Polaris stylelint-polaris**: `conventions/custom-property-allowed-list` flags values that aren't valid Polaris tokens or that use private tokens. `space/global-disallowed-list` bans legacy spacing APIs "so that space is consistent across the Admin". Space tokens are only for padding, margin and gap. — [stylelint-polaris rules](https://polaris.shopify.com/tools/stylelint-polaris/rules); [space-global-disallowed-list](https://polaris.shopify.com/tools/stylelint-polaris/rules/space-global-disallowed-list)
- **Every Layout**: components accept only integer step indices for padding (interpolated to `var(--s${n})`), so arbitrary lengths are impossible at the API level. — [Every Layout: Modular scale](https://every-layout.dev/rudiments/modular-scale/)
- **Carbon**: tokens are fixed across screen sizes; responsive change means stepping along the scale, not inventing values. — [Carbon spacing](https://carbondesignsystem.com/elements/spacing/overview/)

### Inferences (application to bedit / Brood)
- **One spacing table, two units.** A single Brood map (e.g. in `src/ui-kit.blsp` or a new `src/spacing.blsp`) holds primitives in typed units: `{:row 1 :half-row 0.5 :cell 1 :half-cell 0.5 :hairline [:px 1]}`. Semantic tokens alias them: `:card-pad [1 2]` (rows, cells), `:row-inset 1`, `:menu-gap 1`, `:region-gap 0`, `:hover-inset :half`. The density modes are alternative semantic tables.
- **Make the API refuse raw numbers.** As Every Layout does, widget style keys like `:pad`, `:inset` and `:gap` accept only token keywords (`:pad :card`), and the resolver `(space token axis)` returns cells or rows. A raw float throws, or is a contract (`sig`) failure. Brood's runtime-enforced `sig`s are the natural enforcement point (an "accept only token keywords" contract on `ui-pad-amount` and friends).
- **Lint the rest.** Brood equivalent of `ensure-design-token-usage`: a test (like bedit's existing `tests/strict_ratchet_test` ratchet) that greps `src/` for numeric literals in spacing positions (`:inset`, `:pad`, `:gap`, `*…-inset*`, `*…-pad*` defs) outside the spacing module, with a count that may only shrink.
- **Invariant tests on the frame layout.** Property tests over many window sizes and font sizes: (a) every text-bearing region's top is `inset + k·row` for integer k; (b) regions tile with no gap or overlap; (c) the leftover `window_h − inset − n·row` lands in exactly one named place; (d) every popup's interior padding equals its token on all sides. These make the recurring header-line and echo-area gaps a test failure, not a visual surprise.
- **Hairlines are not cells.** Borders should be a device-pixel token drawn *inside* a cell's rect, not a fractional-cell offset, so they never shift the grid. Brood/bedit already have a `*hairline*` notion in `src/view.blsp`.
- **Possible Brood-level gap (prime directive):** a `std/editor/display` notion of *typed grid lengths* (rows vs cells vs device px), with `ui` layout primitives (stack and gap à la Carbon's Stack, inset à la Every Layout) that accept only those, would be a language/toolkit capability usable by any Brood GUI program, not just bedit. Whether it passes the "a caller besides bedit" test depends on whether Brood's observer or REPL GUI would use it, which these notes didn't check.

### Gaps
- No public example found of a TUI framework (ratatui, Textual) linting raw spacing values. Their enforcement is limited to integer cell units in the type system.
- Did not verify how other monospace-grid GUIs (Neovide, Emacs child frames) handle leftover pixel height, which is relevant to the echo-area gap. Worth a follow-up.
