# Anchor the chrome, let the text absorb pixels

bedit's recurring spacing bugs have one cause, and the cure is a layout model, not more tuning. The leftover height (window height minus the inset, mod one row) has to go into the **flexible text body as a partial row**, between the last text line and the bottom pane's mode line. It must not sit above the header line, under the echo area, or be split across both. That is how GNU Emacs in pixelwise mode and VS Code handle it. Every terminal policy (top-left, balanced, centred) leaves some of the remainder next to a chrome band, and bedit has now shipped each of those failures in turn ([Emacs windows.texi](https://raw.githubusercontent.com/emacs-mirror/emacs/master/doc/lispref/windows.texi); [VS Code statusbarPart.ts](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/browser/parts/statusbar/statusbarPart.ts)). In Brood this becomes a small, generic renderer capability: a **seam row** the app declares. Rows above it are anchored to the top, rows from it down are anchored to the bottom, and the remainder sits at the seam, painted and hit-tested by the renderer. bedit's only job is to name the row of its bottom mode line. The rest of the evidence points the same way, towards quiet chrome. Recess the mode line the way the header line was just recessed, separate selection from search tints, put text-emphasis tiers and one spacing table under test, fix light-on-dark glyph weight with linear blending plus a contrast correction, and keep motion off the typing path. Every item below says what to change, why, how to prove it with `gui/render-frame` or `tools/screenshot.blsp`, and whether it belongs in Brood or in bedit.

## Terminal padding policies fail an editor; Emacs's edge-anchored model does not

There are two families of answer to "where do the leftover pixels go". Terminals have no chrome, so they treat the remainder as padding. Ghostty, kitty, Alacritty and foot all offer top-left anchoring (the remainder on the right and bottom) or centring ([kitty.conf](https://sw.kovidgoyal.net/kitty/conf/); [foot.ini(5)](https://codeberg.org/dnkl/foot/raw/branch/master/doc/foot.ini.5.scd); [Alacritty config](https://alacritty.org/config-alacritty.html)). Their own experience is a warning. Ghostty turned balanced padding off by default because resizing **"was too jittery"**, and it caps top padding at half a cell plus the explicit padding because a lot of space above row 0 looks bad ([Ghostty size.zig](https://raw.githubusercontent.com/ghostty-org/ghostty/main/src/renderer/size.zig); [Ghostty reference](https://ghostty.org/docs/config/reference)). foot centres only when the compositor dictates the size, and says centring "may cause 'jumpiness' when resizing" ([foot.ini(5)](https://codeberg.org/dnkl/foot/raw/branch/master/doc/foot.ini.5.scd)). Neovide inherits a cell grid from nvim, and its users report "up to one font-height block of unused grid space" at the bottom ([neovide#140](https://github.com/neovide/neovide/issues/140)). That is exactly bedit's 11 px gap at 600 px and 24 px gap at 613 px today.

Editors with chrome work differently. Emacs pins the minibuffer to the bottom of the frame and each mode line to the bottom of its window. When the frame is not a whole number of lines, "at least one window may get resized pixelwise", and the surplus shows as a partially visible bottom line in that window's body, which `window-body-height` deliberately does not count ([windows.texi](https://raw.githubusercontent.com/emacs-mirror/emacs/master/doc/lispref/windows.texi)). Its internal border is painted in the `internal-border` face, so a margin is never an unpainted gap ([frames.texi](https://raw.githubusercontent.com/emacs-mirror/emacs/master/doc/lispref/frames.texi)). Emacs has hit bedit's current bug too. In bug#19990 a tiling WM left an unpainted strip under the minibuffer, and the fix was `frame-resize-pixelwise`, which hands the pixels to the windows ([bug-gnu-emacs 2015-03](https://lists.gnu.org/archive/html/bug-gnu-emacs/2015-03/msg00102.html)). VS Code's status bar is a constant **22 px** band (`static readonly HEIGHT = 22`), and the editor area absorbs the rest ([statusbarPart.ts](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/browser/parts/statusbar/statusbarPart.ts)).

The steelman for a strip under the bottom row is real: it is what xterm and urxvt do, and a 2024 emacs-devel proposal (`frame-resize-force-char-height`) asked for it so that no window shows a half line ([emacs-devel msg00428](https://lists.gnu.org/r/emacs-devel/2024-02/msg00428.html)). It fits a terminal, where the last row is content. In bedit the last row is the echo area, a chrome band, so the strip reads as the echo area floating off the window edge. The half-line wart is much less visible: it sits inside text the eye already treats as continuing. Nobody replied to that proposal with a decision.

One thing cannot be relied on to make the problem go away: resize increments. ICCCM size hints only "encourage" the window manager. Wayland compositors do not reliably honour increments, and maximised, tiled and fullscreen sizes are never constrained ([ICCCM](https://xorg.freedesktop.org/archive/X11R7.6/doc/xorg-docs/specs/ICCCM/icccm.html); [foot.ini(5)](https://codeberg.org/dnkl/foot/raw/branch/master/doc/foot.ini.5.scd)). The layout has to be correct at every pixel height.

## The layout decision: a declared seam row, remainder above the bottom mode line

This is the section to settle the spacing bugs. The model has five rules, and each one is a testable invariant.

**Rule 1: the inset is a fixed frame on left, right and bottom, painted by whatever band touches it.** ADR-508's edge bleed already does this (`backend/bleed.rs`). Keep it.

**Rule 2: the top edge has no inset when row 0 is a full-width band, which is the header line.** Today's `grid_origin = (inset, 0)` is right whenever the header line is on. When the header line is off, row 0 is buffer text touching the window's top edge with 0 px against 6 px on the sides. That is a smaller version of the same asymmetry. The seam declaration below should carry a `top-inset` flag: bedit sets it to `0` with a header line and to `inset` without one. Screenshot both cases before deciding. The research found no source for this sub-question, so it is judgement.

**Rule 3: bands are laid out in whole rows from their own edge inward.** The header line starts at y = 0. The echo area ends at y = H − inset. Each pane's mode line ends at the bottom of its pane.

**Rule 4: the remainder `r = (H − top − inset) mod row` lands at exactly one place, the seam.** The seam is the row of the bottom-most mode line(s). Panes side by side share that row, so one seam serves any layout bedit can make today. Rows `0..seam−1` sit at `top + k·row`. Rows `seam..last` sit at `H − inset − (last − k + 1)·row`. The `r`-pixel strip between them belongs to the text bodies above the seam. In Emacs terms it is their partial line.

**Rule 5: every row starts on an integer device pixel, and hit-testing inverts the same mapping.** Alacritty floors cell metrics so rows never straddle pixels ([alacritty display/mod.rs](https://raw.githubusercontent.com/alacritty/alacritty/master/alacritty/src/display/mod.rs)). Emacs maps y to a line per window, not with one global division ([windows.texi](https://raw.githubusercontent.com/emacs-mirror/emacs/master/doc/lispref/windows.texi)).

**Where it belongs: Brood first, then a few lines in bedit.** The grid is still uniform in cell units, so bedit stays cell-pure and never sees a pixel. Only the renderer's row-to-pixel map changes. `Renderer::grid_origin` is already the single point that places the grid, and `px_to_cell` / `px_to_cell_frac` already subtract it. A seam turns that into a two-piece function, `row_y(k) = top + k·ch + (k ≥ seam ? r : 0)`, with its inverse in the hit-test. The capability is generic. Any Brood GUI program with a bottom status line (the REPL, the observer, a TUI-style app under `gui-display`) has the same problem. The default, with no seam declared, stays as today: top-anchored, remainder at the bottom. That passes all three prime-directive questions: it is a mechanism, other callers exist, and it versions with the renderer. Implement it in two phases.

*Phase 1 (renderer):* a frame-level op or setting `seam row` (plus the `top-inset` flag). The renderer paints the strip by extending the backgrounds of row `seam − 1` downward, which reuses the bleed machinery with the seam treated as an internal edge. The gutter (mantle), a pane divider and the base text background then continue cleanly into the partial line. Accept one small cost: a current-line highlight on the very last visible line grows by `r` pixels.

*Phase 2 (renderer + bedit):* let the app draw content in a clipped "partial row" at index `seam`. bedit then renders the next buffer line there, half visible, exactly as Emacs does. This also removes the hl-line cost.

*bedit's part:* `src/view.blsp` emits the seam as the row of the bottom mode line. `src/panes.blsp`'s row table is unchanged, because rows are still rows. Mouse folding is unchanged, because the renderer's hit-test already accounts for the seam.

**The alternative, rejected.** Anchoring the whole grid to the bottom and putting the remainder above row 0 makes the header line a variable-height band. It keeps both edges flush, but it moves row 0 on every zoom (the cost ADR-508's split already paid). It also brings back the exact "gap above the first line" whenever the header line is off, which is the opt-in default. And it needs header text that is optically centred in a band of changing height. The seam hides the discontinuity inside text, where Emacs's twenty years of use show nobody minds.

**Verification.** Replace the old `the_vertical_remainder_is_split_above_and_below_at_every_size` guard with a property test in Brood over `gui/render-frame`. For every height in `[H, H + row)` and at least two font sizes, render a frame whose row 0 and last row have distinct band colours, and assert four things. (a) Pixel row 0 is the header colour. (b) Pixel row `H − inset − 1` is the echo-area colour, and the `inset` rows below it are the bled echo colour. (c) No pixel row anywhere is the bare window background unless the frame painted it. (d) `px_to_cell(row_y(k) + 1) == k` for every k. In bedit, add a `tools/screenshot.blsp` sweep at 600, 607 and 613 px with `--header-line` and without it, plus `--zoom` crops of the top 40 and bottom 40 px. The images are the regression record for the user's eye. The screenshot tool currently lives in the `bedit-wt-int4` integration worktree, not on main.

## Quiet chrome: recess the mode line, tier the greys, separate the tints

The cross-editor pattern for de-emphasising chrome uses three tools, in order: a **small background step** (VS Code's chrome surface `#181818` against the `#1F1F1F` editor is only **1.08:1**), **secondary-grey text** (VS Code chrome text 6.55:1 / APCA Lc 48 against 10.26:1 / Lc 74 for code), and **no bold or borders**, with weight and accent kept for state ([vscode dark_modern.json](https://raw.githubusercontent.com/microsoft/vscode/main/extensions/theme-defaults/themes/dark_modern.json)). JetBrains' Islands theme sets its status-bar and toolbar borders fully transparent ([IntelliJ SDK: Islands](https://plugins.jetbrains.com/docs/intellij/supporting-islands-theme.html)). Modus recipes hide fringes and dividers and pad with `internal-border-width` instead of lines ([Modus manual](https://protesilaos.com/emacs/modus-themes)). Today's header line (subtext0 on mantle, 7.89:1 / Lc 57) now sits right in that secondary tier, so it was a good move.

**The mode line goes against the pattern.** `face-modeline` is `{:fg *text* :bg *surface0*}`: a *raised* surface (1.30:1 over base) carrying full-brightness text. Catppuccin's own role map puts secondary panes on Mantle/Crust and labels in Subtext ([Catppuccin style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md)). Change the active mode line to subtext0 or subtext1 on mantle, reserve `text` and an accent for the buffer name and state (modified, a failing check), and take the inactive one down to overlay1. Prot's `spacious-padding-subtle-frame-lines`, which swaps the filled bar for a hairline, is the next notch if this is still too loud ([spacious-padding](https://protesilaos.com/emacs/spacious-padding)). This is bedit work in `src/theme.blsp` and `src/statusbar.blsp`.

**Make the tiers tokens, and test them per theme.** Use APCA's levels: Lc 75 is the minimum for body text, Lc 60 for content text that is not body text, Lc 45 for larger or heavier text, Lc 30 the floor for any text, and Lc 15 the floor for a discernible divider ([APCA in a Nutshell](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)). They map onto Mocha as follows: code = text (Lc 80), primary chrome = subtext1 (Lc 68), secondary chrome = subtext0/overlay2 (Lc 57–46), tertiary = overlay1 (Lc 35), decorative = overlay0/surface2 (Lc 26–17). Add `:fg-code`, `:fg-chrome`, `:fg-chrome-dim` and `:fg-decor` tiers that the `defchrome` faces reference. A later "make chrome subtler" pass is then one edit, and every theme in `src/themes.blsp` inherits the hierarchy. Verify with a pure test in bedit over the theme registry that computes APCA Lc for each face pair and asserts the tier bands. The contrast formula itself (WCAG ratio plus APCA Lc) is generic arithmetic. It belongs in a Brood std colour module if one exists, because a second caller is concrete: a vt minimum-contrast option like kitty's `text_fg_override_threshold` ([kitty.conf](https://sw.kovidgoyal.net/kitty/conf/)). Otherwise keep it in bedit until that caller appears.

**Selection and lazy matches currently look the same.** Both `face-region` and `face-isearch-lazy` use surface2 (2.46:1 over base), which is far heavier than Catppuccin's spec of selection = Overlay 2 at **20–30% opacity** ([Catppuccin style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md)). Zed's One Dark uses selection at about 24% alpha and search matches at 40% of the same blue ([zed one.json](https://raw.githubusercontent.com/zed-industries/zed/main/assets/themes/one/one.json)). Change the region to a 25% overlay2 blend over base (it falls between surface0 and surface1) and the lazy matches to a low-alpha hue tint (teal at 20–25%). Keep the strong yellow fill for the active match only. Keep a hue budget: red for errors only, yellow/peach for warnings and the active match, teal for info and other matches, blue for selection. State uses backgrounds and syntax uses foregrounds, so the two never collide ([tonsky.me](https://tonsky.me/blog/syntax-highlighting/)). Verify with `gui/render-frame` on a buffer that has a region and a lazy match on screen at the same time: sample one pixel of each and assert the colours differ and stay within their tier.

**The gutter and line numbers.** VS Code, Zed and Modus give the gutter the editor's own background and dim only the numbers. bedit's mantle gutter plus a mantle header line forms an L-shaped frame of chrome around the code. Try `face-gutter-bg` = base in a screenshot comparison. Raise line numbers from overlay0 (Lc 26) to Catppuccin's specified overlay1 (Lc 35), and add a lavender active line number as the "you are here" mark ([Catppuccin style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md)). All of this is bedit theme work.

**Syntax restraint, as an option rather than the default.** Tonsky's argument is "if everything is highlighted, nothing is highlighted". Colour definitions and literals, make comments readable rather than hidden, leave keywords plain, dim punctuation, and use no bold or italic ([tonsky.me](https://tonsky.me/blog/syntax-highlighting/)). The empirical record is equivocal. Hannebauer et al. found no comprehension benefit for about 390 novices, while Sarkar's 10-person eye-tracking study found faster task completion that faded with experience ([Hannebauer 2018](https://unpaywall.org/10.1007%2FS10664-017-9579-0); [Sarkar 2015](https://advait.org/files/sarkar_2015_syntax_colouring.pdf)). So ship a "Mocha calm" theme entry rather than rewriting the default. For Brood and the Lisps, dimmed parentheses plus coloured top-level `def` names get the effect cheaply. `:rainbow-delimiters` pulls the other way, and it should default to off or to low chroma. Note one property of Mocha: mauve keywords sit at Lc 61, *below* the text colour, while yellow and green sit at Lc 78–88, *above* it, so the palette already varies lightness by role.

## Type and rendering: round every metric, fix light-on-dark weight in the blender

**bedit's line height of 1.25 is defensible.** Editors use 1.2 (JetBrains) to 1.35 (Monaco off macOS) for "standard" density, and Zed's comfortable setting is 1.618 ([IntelliJ font settings](https://www.jetbrains.com/help/idea/settings-editor-font.html); [monaco fontInfo.js](https://app.unpkg.com/monaco-editor-core@0.52.2/files/esm/vs/editor/common/config/fontInfo.js); [Zed commit #2718](https://git.secluded.site/zed/commit/415b8f01472ab50f8852516b6cb2f7c636f9e132)). Butterick recommends 120–145% for text ([Practical Typography](https://practicaltypography.com/line-spacing.html)). No code-specific study backs any one number, so leave it alone. Line height is also the strongest density lever, since every row-measured thing scales with it.

**Vertical placement inside the cell (Brood renderer).** Use CSS half-leading: `L = cell − (A + D)`, half above and half below, with A and D taken from OS/2 typo metrics (hhea as a fallback) and the font's line gap ignored when an explicit ratio is set ([CSS Inline 3](https://www.w3.org/TR/css-inline-3/); [Glyphs, vertical metrics](https://glyphsapp.com/learn/vertical-metrics)). Round both `cell` and the baseline to whole pixels; Monaco rounds explicitly ([fontInfo.js](https://app.unpkg.com/monaco-editor-core@0.52.2/files/esm/vs/editor/common/config/fontInfo.js)). The renderer already rounds px per em (`recompute`). Extend that to an asserted baseline. Centre UI glyphs (gutter marks ● ✓ ✗ ⚠, chevrons) on baseline + x-height/2 rather than on the ascent/descent box, which puts them visibly low, and expose a baseline adjustment as Ghostty (`adjust-font-baseline`) and kitty (`modify_font baseline`) do ([Ghostty reference](https://ghostty.org/docs/config/reference); [kitty.conf](https://sw.kovidgoyal.net/kitty/conf/)). Verify with a `gui/render-frame` test: render "Hxg" at three sizes and assert the cap top and baseline land on the same pixel offsets in every row, and that the ink is centred within ±1 px of the half-leading prediction.

**Light-on-dark thinness (Brood GPU painter).** Blending coverage in gamma space makes light text on a dark background look thin ([FreeType text rendering](https://freetype.org/freetype2/docs/hinting/text-rendering-general.html)). bedit's soft grayscale text on Mocha is that textbook case. The modern fix is linear blending plus a luminance-dependent alpha correction. Ghostty defaults to `linear-corrected` off macOS, and Zed shipped a perceptual gamma of 1.8 with a DirectWrite-style enhanced contrast of 1.0 ([Ghostty reference](https://ghostty.org/docs/config/reference); [Zed commit #38862](https://git.secluded.site/zed/commit/e72021a26bf3e7e31d736eaaea89d6914149a9bf)). Use slight, vertical-only hinting, as FreeType and Ghostty do. Expose gamma and contrast as tunables, and a grayscale/subpixel switch like Zed's `text_rendering_mode` ([Zed docs commit #46358](https://git.secluded.site/zed/commit/b8dfc31fcd29585328655a5d2b72a215273cb4bd)). A type designer's alternative is a per-polarity weight: Commit Mono recommends 400 for dark mode and 450 for light ([Commit Mono](https://commitmono.com/)). Verify by rendering a block of `text`-on-`base` glyphs through both the CPU and GPU painters with `gui/render-frame`. Assert that the mean ink luminance on the GPU path is within a tolerance of the CPU (LCD) path, and that a correction-off run is measurably lighter, so the knob is proven to work.

**Ligatures (Brood shaper), low priority.** Shape with per-feature tags (`calt`, `liga`, `ss0N`) rather than one switch. Turning off `calt` also kills Monaspace's texture healing ([Monaspace](https://monaspace.githubnext.com/)). Offer kitty's "off under the cursor" mode ([kitty.conf](https://sw.kovidgoyal.net/kitty/conf/)). Butterick's objection that `!=` drawn as `≠` is ambiguous argues for a default of off ([Practical Typography](https://practicaltypography.com/ligatures-in-programming-fonts-hell-no.html)).

## One spacing table, whole rows for text, motion only for spatial jumps

**Spacing.** Every major design system uses one base unit, a closed set of named steps and few sub-unit steps. Carbon's scale is 2–160 px, and it says off-scale values "should be avoided" ([Carbon spacing](https://carbondesignsystem.com/elements/spacing/overview/)). Atlassian forbids raw pixels in favour of tokens and lints for them ([Atlassian spacing](https://atlassian.design/foundations/spacing); [ensure-design-token-usage](https://atlassian.design/components/eslint-plugin-design-system/ensure-design-token-usage)). Every Layout's components accept only integer step indices, so an arbitrary length cannot be expressed at all ([Every Layout](https://every-layout.dev/rudiments/modular-scale/)). In a cell grid the units are **one row vertically and one cell horizontally**. A row is about twice a cell, so optically equal padding is 1 row to 2 cells, which is ratatui's `Padding::proportional` rule ([ratatui Padding](https://docs.rs/ratatui/latest/ratatui/widgets/block/struct.Padding.html)). bedit's popup card pads "one cell on every edge", so it looks thinner at the sides than at the top. Its loose constants (`*sb-hover-vinset* 0.16`, `*sb-hover-pad* 0.55`, `:inset 2` / `:gap 3` overrides in `src/view.blsp`) are the off-scale values the systems warn against.

Do this in bedit. Create one table in `src/ui-kit.blsp` with the primitives `{0, hairline (device px), half, 1, 2, 3}` and semantic tokens (`:card-pad [1 2]`, `:row-inset`, `:menu-gap`, `:hover-inset :half`). Widget keys take token keywords only, enforced by a `sig`. Rule: **anything that holds text moves by whole rows. Sub-row values only decorate inside a row** (a pill inset, a radius, a hairline) and never move a baseline. The container owns the gap, as in Carbon's Stack, so no widget adds space outside its rectangle. That is how the "two neighbours each own half a gap" bugs arise. Verify with a ratchet test modelled on `tests/strict_ratchet_test` that counts numeric literals in `:pad` / `:inset` / `:gap` positions outside the table (the count may only shrink), and a `gui/render-frame` test that measures each popup's inner padding on all four sides against its token. Typed grid lengths in `std/editor/display` (rows vs cells vs px) would be a Brood capability only once a second program such as the observer wants them. That has not been checked yet, so this stays in bedit for now. A density switch, if bedit ever wants one, is an alternative token table plus a line-height change. It should not be a 0.75 multiplier, which produces fractional cells ([Zed ui_density.rs](https://git.secluded.site/zed/blob/main/crates/theme/src/ui_density.rs?raw=1)).

**Latency is the largest part of "calm".** MSR's demo put 10 ms as noticeable and under 1 ms as paper-like, and at 10 characters a second a p99.9 event happens about every 100 seconds, so the tail is what users feel ([Dan Luu](https://danluu.com/term-latency/)). Fatin argues that jitter hurts more than a steady delay and targets 1–5 ms for the editor's own processing and paint ([Typing with pleasure](https://pavelfatin.com/typing-with-pleasure/)). Zed's architecture exists to fit the **8.33 ms** frame at 120 Hz ([Zed blog](https://zed.dev/blog/videogame)). Brood should timestamp key arrival and the paint that shows it. bedit's slow-turn log should report key-to-paint as a p50/p99/p99.9 distribution. Measuring belongs on CI or the other machine, not on this desktop.

**Motion.** Good editor motion is short, decelerating, interruptible and reserved for spatial changes. VS Code's smooth caret lagging behind typed text is the canonical failure: it was acknowledged as "a real issue" and closed as not planned ([vscode#295648](https://github.com/microsoft/vscode/issues/295648)). Neovide uses 40 ms for one- or two-character cursor moves, about 150 ms for jumps and 300 ms for scroll, and can disable animation in insert mode ([Neovide configuration](https://neovide.dev/configuration.html)). Pulsar's sample settings give a fade of about 280 ms ([pulsar](https://protesilaos.com/emacs/pulsar)), and Apple asks apps to honour Reduce Motion ([Apple reduced-motion criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria)). In bedit: never animate the result of a keystroke. Make the glide retarget from its current position, and drop it entirely under key repeat. Keep the pulse at about 280 ms for 5+ line jumps (the current threshold). Add one `:reduce-motion` setting that makes glide and pulse instant or static. Reading the OS reduced-motion preference is a Brood host capability, since any GUI program wants it. Verify with model tests that a held C-v produces no glide frames and that `:reduce-motion` yields zero animation timers.

**Messaging.** Keep information in the periphery and let the user move it to the centre ([Weiser & Brown](https://calmtech.com/papers/designing-calm-technology)). Use a muted face for informational echo-area messages and the error face only for failures. Show a background job's chip only once the job passes about 1 s, which is Nielsen's attention threshold ([NN/g](https://www.nngroup.com/videos/3-response-time-limits-interaction-design/)), so fast jobs never flicker. Keep which-key behind a delay; upstream's default is 1.0 s ([which-key README](https://github.com/justbur/emacs-which-key)). All of this is bedit work, testable as model tests.

## Conclusion

Every spacing bug bedit has had came from the same source: chrome bands treated as ordinary grid rows, with a padding policy written for an editor that has no chrome. The fix is not a better padding policy. It is to admit that an editor's grid has two anchors and to say so in the renderer once, as a declared seam, so bedit can never again spend pixels by accident. The layout then becomes a property that can be proved over every window height instead of checked by eye one screenshot at a time. The new frame-capture primitive is what makes that affordable.

The colour and typography findings follow the same logic. Calm comes from a small number of deliberate tiers (one surface step, four grey levels, a hue budget, a spacing table) encoded as tokens and enforced by tests, not from taste applied face by face. Light-on-dark weight is the one place where the right fix is in the blender, not the theme. The evidence for any particular highlighting scheme is weak, so the defensible stance is to offer restraint as a variant and to measure what is measurable: contrast, pixel placement and tail latency.
